# API tokens and MCP

Owlee has a JSON API that only the web app uses. It accepts the session cookie and nothing else. This design adds personal API tokens with granular scopes and a remote MCP endpoint, so scripts and AI tools (Claude Code, Cursor) can read and triage errors. Error tracking comes first. Status and Analytics get scopes later, through the same mechanism.

The model follows Coolify ([permissions](https://coolify.io/docs/api/permissions), [tokens](https://coolify.io/docs/core/security/credentials/api-tokens)). A token belongs to one user in one workspace. It has a set of abilities, it can never do more than its owner's current role allows, and Owlee shows it once. Owlee splits the abilities per product (`errors:read` and not a global `read`), so a token for error triage cannot touch monitors.

## Decisions

| # | Decision | Why |
|---|---|---|
| D1 | A token belongs to one user and one workspace. Its workspace comes from the token, not from `X-Owlee-Workspace`. If that header is present and names another workspace, the result is 404. | Same as a Coolify team token. One token cannot cross workspaces. |
| D2 | Scopes are `<product>:<access>`, with access `read`, `write`, or `delete`. This release has `errors:read`, `errors:write`, `errors:delete`. There is no `root` scope. | Per product is more granular than Coolify's global abilities. Without `root`, adding a product never widens old tokens. |
| D3 | The request method gives the access level. `GET` and `HEAD` need `read`, `DELETE` needs `delete`, and the other methods need `write`. A product router declares its product with a layer. | One rule for each product instead of a scope on each route. |
| D4 | Default deny. A token can only call a route whose router declares a product. Other cookie routes (workspaces, members, monitors, tokens, privacy) return 403 `token_not_allowed` for a token. | A new route stays closed to tokens until someone opens it. |
| D5 | The `Member` extractor accepts `Authorization: Bearer owl_…` as well as the session cookie. A bearer token wins over a cookie. The handlers do not change. The extractor checks membership on every request, so the existing role checks (`require_editor`) still apply. | The token never has more access than its owner has now. Removing a member or disabling a user ends their tokens at once. |
| D6 | At creation, a workspace `member` can choose read scopes only. Owners and admins can choose all scopes. | The UI must not offer a scope that will always return 403. |
| D7 | The format is `owl_` + 32 random bytes in base64url (43 characters). Owlee stores the SHA-256 hash and a 12-character display prefix. Tokens can expire after 7, 30, 90, or 365 days, or never. | The prefix helps secret scanners and lets users identify a token in the list. The hash is the same as for sessions. |
| D8 | `last_used_at` updates at most once every 5 minutes. | The same throttle as sessions. It prevents a write on each request. |
| D9 | Tokens cannot manage tokens. The `/api/api-tokens` routes accept the session cookie only. | A leaked token cannot make more tokens for itself. |
| D10 | MCP is at `POST /api/mcp` with Streamable HTTP. Every response is a single `application/json` body. There are no sessions and no SSE, so `GET` and `DELETE` return 405. The endpoint supports the `initialize` handshake (2025-03-26, 2025-06-18, 2025-11-25) and also `server/discover` (2026-07-28). | Plain JSON is valid for both protocol versions, and current clients still send `initialize`. |
| D11 | MCP accepts bearer tokens only, not the cookie. A request whose `Origin` is not `public_origin` gets 403. | The MCP spec requires Origin validation. With bearer only, a browser cannot use the endpoint. |
| D12 | An MCP tool is a row in a table. Each row has a name, a description, an input schema, a method, and a path. `tools/call` sends a request with the caller's `Authorization` header to the errors router in the same process. `tools/list` shows only the tools that the token's scopes allow. | Authorization has one source. MCP cannot get more access than the REST API gives. |
| D13 | A token can have a resource limit: all resources (the default), or a list of projects and error apps. A listed project covers all of its apps, including apps added later. A listed app covers only that app. | This is the same as Coolify's "selected projects, environments, or resources". Projects apply to all products, and apps apply to Errors only. |
| D14 | A resource outside the limit is hidden. A list leaves it out, and a lookup by id returns 404, the same as a resource in another workspace. A limited token can create an app only in a listed project. Otherwise it gets 403 `resource_not_allowed`. | The token must not show that hidden resources exist. Creation has no existing resource to hide, so 403 is correct there. |
| D15 | The UI shows one access level for each product: No access, Read, Write, or Delete. Each level includes the levels before it, so Delete stores `read`, `write`, and `delete`. The API still stores and accepts single scopes. | This is the Orbit pattern. It gives one choice for each product instead of three checkboxes that depend on each other. |
| D16 | **Rotate** gives the token a new secret and prefix and keeps its id, name, scopes, resource limit, expiry, and paused state. The old secret stops working at once. The response shows the new token once. | This is Coolify's Roll. The token's integrations are updated in one step, and no settings are lost. |
| D17 | **Pause** sets `paused_at`. A paused token gets 401 until the user resumes it. Resume clears `paused_at`. Expiry does not stop while the token is paused. | This is Coolify's Pause. It is a reversible way to turn off a token that might have leaked. |
| D18 | Rotate and Revoke ask the user to type the token name to confirm. Pause and Resume do not ask. The row actions are in a "…" menu. | This follows Coolify. A wrong rotate or revoke breaks integrations, and a pause can be undone. |
| D19 | Owlee publishes an OpenAPI 3.1 document for the token API (every route in `product_routes`). The file is `apps/server/openapi/v1.json` in the repository, and the binary includes it. Anyone can read it, without a login, at `GET /api/v1/openapi.json`. `GET /api/openapi.json` returns the same document, because it always serves the newest version. | Agents and code generators need one source of truth that they can fetch. A versioned URL stays stable when v2 comes. |
| D20 | The document's major version is the API version (`v1` in the URL). `info.version` is a semver string such as `1.0.0`: add a field or a route, and the minor number goes up. Remove or change something, and the API becomes `v2`, with a new file and URL. The v1 file stays as long as v1 routes exist. | This is the usual contract for a public API. Clients can trust that v1 does not break. |
| D21 | When the document is served, `servers` is set to `<public_origin>/api`. The response has `Access-Control-Allow-Origin: *` and a short cache time. | A client that fetches it from any instance gets that instance's URL. Browser tools on other origins can read it, and it has no secrets. |
| D22 | A contract test calls each operation in the document through the real router with a token, and checks the status and the response body against the document's schema. | A document written by hand drifts. The test fails when a route or a response shape changes without the document. |
